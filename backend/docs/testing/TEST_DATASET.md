# Test Dataset

This document describes the seeded API/Postman testing dataset produced by
`database/seeders/{UserSeeder,FavoriteSeeder,WatchedTitleSeeder}.php`
(orchestrated by `DatabaseSeeder`).

## Scope

Cinematch does not store movies, TV shows, search results, title details, or
recommendations in the database — that data comes from the ML model /
dataset at request time. The database only stores **application data
generated by users**: accounts, Favorites, and Watched History.

This dataset therefore seeds **only**:

- `users`
- `favorites`
- `watched_titles`

It never seeds movie/title records or recommendation data. Title metadata
that appears in `favorites`/`watched_titles` (name, type, genres, release
year) is a fabricated snapshot, matching the shape the ML layer would have
returned at write time — it exists purely to make seeded rows realistic, not
to represent real catalogue data.

`taste_profiles` is not seeded: it is a scaffolded table with no reader or
writer anywhere in the application (dead schema at the time of writing).

## Running the seeders

```bash
php artisan migrate:fresh --seed
# or, on an already-migrated database:
php artisan db:seed
```

All seeders use `updateOrCreate`, so re-running `db:seed` is safe and will
not raise duplicate-key errors or duplicate rows.

### Testing purpose per user

- **`user1@example.com` — Fresh User.** Zero signals. Use to test the
  brand-new-account / `stranger` stage: registration → login → empty
  `GET /favorites`, empty `GET /history`, and Home's non-personalized
  ("Popular only") response.
- **`user2@example.com` — Explorer User.** 4 total signals (2 favorites, 2
  watched, with one title — *The Dark Knight* — deliberately present in
  **both** tables). Use to test the `explorer` stage of Home, and to verify
  a title can independently exist in Favorites and Watched History without
  any coupling between the two tables.
- **`user3@example.com` — Regular User A.** 12 signals (6 favorites, 6
  watched, no overlap between the two — favorites are movies, watched are
  TV shows). Use to test the `regular` stage, including the "Because You
  Watched" Home section, which depends on Watched History specifically.
- **`user4@example.com` — Regular User B.** 8 signals, deliberately sharing
  two favorited titles (*Get Out*, *La La Land*) and one watched title
  (*Narcos*) with `user3`. Use this pair to test **cross-user isolation**:
  confirm `GET /favorites` and `GET /history` for one user never leak the
  other user's rows, even when both users favorited/watched the same title
  (each row is scoped by `user_id`, so the same `title_name` can legally
  exist once per user across the whole table).
- **`user5@example.com` — Loyal User.** 22 signals (12 favorites, 10
  watched). Favorites intentionally exceed 10 records with `added_at`
  spread 3 days apart (most recent first) so the Home feature's
  recency-weighted "loyal" logic (e.g. weighting the 5 most recent
  favorites, falling back to a popular pool beyond the 10th) can be
  exercised meaningfully.
- **`user6@example.com` — Heavy User.** 60 signals — the same 30 movie
  titles appear in **both** Favorites and Watched History (allowed, since
  the tables are independent), with timestamps spread ~12 days apart across
  roughly a year. Use for stress/pagination/large-payload testing and to
  confirm performance doesn't degrade with a high signal count.

## Favorites

Seeded by `FavoriteSeeder` using a fixed title catalogue
(`database/seeders/Support/TitlePool.php`) — never randomized. Each user's
slice of the pool, and the spacing between `added_at` timestamps, was chosen
deliberately (see table above and per-user notes). No two favorites for the
same user share a `title_name`, honoring the `unique(['user_id',
'title_name'])` constraint.

## Watched History

Seeded by `WatchedTitleSeeder`, structurally mirroring `FavoriteSeeder`
(same title pool, same non-random intent, same `unique(['user_id',
'title_name'])` constraint — enforced independently of Favorites). Where a
user's watched titles overlap with their own favorites, or with another
user's records, it is intentional (see per-user notes above), not
incidental.

## Relationships & data integrity

- Every `favorites.user_id` / `watched_titles.user_id` references a user
  created by `UserSeeder` — no orphan rows.
- Both tables enforce `unique(['user_id', 'title_name'])`; the seeders use
  `updateOrCreate` keyed on that same pair, so re-seeding is idempotent and
  cannot violate the constraint.
- `title_type` is always `movie` or `tv_show` (backed by the `TitleType`
  enum) — never free text.

## Testing notes

- **Auth flow:** log in as any user via `POST /auth/login` with their email
  and `password` to obtain a token, then call `GET /auth/me`,
  `GET /favorites`, `GET /history`, and `GET /home` as that user.
- **Stage-based Home testing:** use `user1` → `user2` → `user3`/`user4` →
  `user5`/`user6` to walk through `stranger` → `explorer` → `regular` →
  `loyal` without reseeding between requests.
- **Cross-user isolation:** always test with the `user3`/`user4` pair, since
  they share overlapping title names on purpose — the sharpest way to catch
  a query that's missing a `user_id` scope.
- **Duplicate-write testing:** `POST /favorites` or `POST /history` with a
  `title_name` a seeded user already has (e.g. `user3` + "Parasite") should
  be used to test the unique-constraint/duplicate-handling path.
- **Delete-by-title-name testing:** `title_name` matching is exact-string
  and case-sensitive in this app; use the exact casing from the tables
  above (e.g. `The Dark Knight`, not `the dark knight`) when calling
  `DELETE /favorites/{title_name}` or `DELETE /history/{title_name}`.
- **Fresh-state testing:** `user1@example.com` has zero rows in both tables
  and is the fastest way to test empty-state responses without truncating
  data other tests depend on.
- Re-run `php artisan db:seed` at any point to restore all seeded users to
  their documented state — it will not duplicate or corrupt data.
